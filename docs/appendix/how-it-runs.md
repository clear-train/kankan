# 一次调用走了几步：从命令行到 MCP

这一页只回答两个问题：你说的 harness 到底在干什么，以及从命令行工具到 MCP，中间走了几步。

先给结论：harness 是模型外面那层壳，管四件事——把工具清单翻译成模型能读的样子，把模型说的调用真发出去，把结果塞回去再问一轮，以及决定什么时候重试、什么时候放弃、上下文满了删哪段。模型只做一步：给一段话，接下一段。二十步的活，剩下的十九步都在这层壳里。细节见[Harness](/words/41-harness)。

## 第一步：命令行

最早的做法是人和模型各干一半。模型写一段命令或者一段脚本，你复制到终端里跑，报错贴回去，它再改。脏活在人身上：执行、看报错、判断该不该重来、把哪个文件贴给它。

这一步的好处是可控，坏处是不可自动化。人成了循环里最慢也最贵的那一环，而且人会把上一步的错记得比模型清楚，于是错得越来越隐蔽。

## 第二步：函数调用

模型不再输出一段自然语言命令，而是输出一小段结构化内容：调用哪个工具、传什么参数。宿主程序按约定解析，真去执行，把返回值塞回上下文。开发者要做的变成了「登记函数」：名字、说明、参数格式。

脏活从人手里挪到了宿主程序里。好处是循环能自己转起来；新问题是有几家人就有几套登记方式，换个模型就得重写一遍集成。

## 第三步：MCP

2024 年 11 月 25 日，Anthropic 把这套「登记」标准化了，叫 Model Context Protocol（[发布公告](https://www.anthropic.com/news/model-context-protocol)）。工具做成独立服务，自己声明能干什么、要什么参数，客户端去发现、去连接、去调用，不必为每个模型单独写一遍。

2025 年 12 月，协议被捐给 Linux 基金会下的 Agentic AI Foundation，MCP 从一家公司的接口变成了多家共管的规范（[MCP 博客](https://blog.modelcontextprotocol.io/posts/2025-12-09-mcp-joins-agentic-ai-foundation/)）。

脏活再挪一次：从每个应用的代码里，挪到协议和它的实现里。写工具的人只写一遍，用的人只连一次。

## 三步之间，什么变了

模型本身没有变强。同样的模型，在命令行时代就要靠人补全循环，在函数调用时代能自己跑几轮，到 MCP 时代能接上一整套别人写好的工具。

变的是脏活的位置：人 → 宿主程序 → 协议。这也解释了为什么同一个模型换套壳，成绩会差一截——壳变厚了，能兜住的错误就多了。

MCP 解决的是「怎么连上」，不解决「连上之后干得对不对」。工具能发现，不代表工具可靠；参数能声明，不代表模型会用。壳越标准，越容易让人忘掉它只是壳。

判断一个 harness 好坏，还是那句土话：把壳拆了重装一遍，任务成功率动不动。不动，问题不在壳；动，说明你之前一直在给模型擦屁股，还以为是模型不行。
