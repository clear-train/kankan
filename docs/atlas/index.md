# 卷七 · 编年史：每家一条线，每条线一个寿命

卷六写的是「谁在什么时候做了什么」，讲的是来路。这一卷不讲来路，讲**现在还能撑多久**。

同一件事，两种问法。问「它是怎么来的」，得到的是故事；问「它还能用几年」，得到的是判断。饭桌上真正让人记住你的，通常是后者——因为前者谁都能百度到，后者要有人替你算。

## 这一卷怎么读

每篇写一个模型家族，五节固定：

- **这一族怎么长出来的**：按年份写三到五步，每步只写「换掉了什么」。
- **技术路线**：只说这一族内部真实存在的分歧。没有分歧就写没有，不编。
- **现在谁在用**：谁在付钱、用它做什么、有没有被换掉。
- **预期寿命**：这一卷的落点，下面单说。
- **参考**：每条带链接和访问日期。

## 预期寿命怎么算

先说明白：这是估计，不是统计。任何人给你一个精确到月的模型寿命，都是在卖你东西。

算法只有三层，问三个问题：

1. **它还是默认选择吗？** 一个开发者要新建项目，第一个想到的是不是它。不是，就是已经过气了，只是还没下架。
2. **还有人愿意为它单独付钱吗？** 云厂商还在单列价格、企业还在单独采购，说明它仍是商品；价格被并进套餐、变成「赠送额度」，说明它变成了零件。
3. **它的接口还在长吗？** 文档三个月没更新、SDK 停止维护、模型卡只剩勘误，这三件事同时出现，基本可以判定进入维护期。

区间一律给两个数字。下限是「新项目开始不选它」，上限是「老项目也懒得迁」。中间那段时间，是这一族最赚钱也最无聊的日子。

## 三种读法

- **要选型**：先看「现在谁在用」和「预期寿命」，再看技术路线。技术路线回答「为什么便宜」，寿命回答「值不值得迁」。
- **要在饭桌上说话**：只看每篇的「预期寿命」一节，记住区间和依据，别的都可以现编。
- **想反着读**：从最老的一篇往前读，看每一族怎么从「唯一选择」变成「历史包袱」。这条线读完，你对任何新发布都会冷静很多。

## 收录标准

一条：**能画出这条线的寿命曲线**。做不到的不收，因为那就退回成家谱了。

这一卷会一直被改。模型半年一代，寿命判断一年一修，过期的判断不删，标上「当时的判断」留在原地——**判断错了比没判断有用**。
